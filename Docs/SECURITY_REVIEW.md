## 1. ما هو مؤكد سليمًا (بدليل)

## 2. S-01 — إجبار تغيير كلمة المرور الافتراضية (نُفِّذ في Phase 2)

**الجذر (من التقرير الفني)**: التعليق في `UserBLL.cs:117` كان يعد بأن كلمة
`Admin@123` «تُغيَّر عند أول دخول» دون أي آلية تنفّذ ذلك.

**التنفيذ:**
1. عمود جديد `Users.MustChangePassword YESNO` — يضاف تلقائيًا للقواعد القديمة
   عبر `DbInitializer.EnsureColumn` (idempotent، بدون فقدان بيانات) وموجود
   في `Database/ModernTime_Schema.sql` للقواعد الجديدة.
2. حساب الـ bootstrap admin يُنشأ بالعلم `MustChangePassword = true`.
3. `UserBLL.Login` يُصحِّح العلم وقت الدخول: العلم المخزّن **أو** مطابقة
   كلمة الدخول للقيمة الافتراضية المعروفة (يغطي القواعد المُرقَّاة القديمة
   بدون أي فحص كتابي وقت الترقية).
4. `FrmLogin`: عند العلم → نافذة تغيير **إلزامية** (`FrmChangePassword`
   بنمط mandatory: تعبئة مسبقة لكلمة الحالية + منع الإغلاق قبل النجاح)، ثم
   تحقق قارئ جديد `MustStillChangePassword` — إن بقي العلم تُمسح الجلسة
   ويبقى المستخدم في شاشة الدخول. لا وصول للنظام قبل التغيير.
5. `ValidatePassword` يمنع اختيار القيمة الافتراضية ككلمة مرور جديدة نهائيًا.
6. `ResetPassword` (إعادة تعيين المشرف) يضبط العلم = true: كلمة المشرف
   المؤقتة تُغيَّر إلزاميًا عند أول دخول للمستخدم — المشرف لا يعرف السر النهائي.
7. `ChangePassword` يمسح العلم (DAL) ويبقى مسجَّلًا تدقيقيًا (`Users.ChangePassword`).

**حالة الاختبار**: مجمَّع عبر CI فقط — سيناريوهات الدخول الإلزامي تحتاج
اختبارًا على جهاز فعلي (انظر §6).

## 3. S-02 — PBKDF2 (غير منفَّذ بعد — الخطة)

الحالي: SHA-256 بتكرار واحد (سريع الحساب = أضعف ضد التخمين بجهاز حديث).
الخطة المعتمدة (Phase 8 من خطة التقرير الفني): `Rfc2898DeriveBytes`
(متوفر في .NET 4.0) مع عدد تكرارات مخزّن + إصدار خوارزمية في التخزين،
وترقية تدريجية عند كل دخول ناجح (تحقق بالقديم → إعادة تجزئة بالجديد).
لم يُنفَّذ في هذه المرحلة تجنبًا لخلط تغييرَين أمنيين في دفعة واحدة.

## 4. B-01 — سلامة النسخ الاحتياطي (نُفِّذ في Phase 2)

- كل نسخة تُتحقق **بعد إنشائها** مباشرة (`VerifyBackupFile` يفتح النسخة
  كقاعدة Jet كاملة) — النسخة التالفة تُسجَّل `Status='Failed'` مع تدقيق
  `Backup.VerifyFailed` ويُرفض الإكمال برسالة عربية صريحة.
- `LastBackupTime` يعدّ `Status='Completed'` فقط → النسخ الفاشلة لا تُكتَم
  زمنيًا فيتوقف النسخ التلقائي، بل يُعاد المحاولة.
- الاستعادة كما هي: تتحقق من الملف قبل النسخ + تنشئ نسخة أمان PreRestore
  (والتي أصبحت الآن متحققًا منها هي أيضًا).

## 5. مخاطر معروفة مقبولة (موثقة، بلا إجراء حالي)

| الخطر | السبب المقبول |
|-------|----------------|
| قاعدة Access بلا كلمة مرور | قيد بيئة التشغيل المعتمد (Jet + مشاركة ملف)؛ الحماية عبر صلاحيات التطبيق والتدقيق. يُراجع عند أي تغيير بيئة |
| كلمة المرور تمر بالنص عبر WinForms | ضمن الشبكة المحلية؛ لا نقل شبكي للتطبيق نفسه |
| salt/hash في نفس الصف | نمط معروف في Jet بلا تشفير ملفات؛ الترقية لـ PBKDF2 ترفع كلفة التخمين جذريًا |

## 6. ما يحتاج اختبارًا على جهاز فعلي

1. دخول admin/Admin@123 على قاعدة جديدة → نافذة التغيير الإلزامي + منع الإغلاق + الدخول بعد النجاح.
2. نفس السيناريو على قاعدة قديمة مُرقَّاة (علم NULL + كلمة افتراضية) → حجب أيضًا.
3. إعادة تعيين كلمة مرور مستخدم من المشرف → دخول المستخدم يفرض التغيير.
4. نسخة احتياطية على قاعدة حية → Status=Completed، والاستعادة منها تنجح.
